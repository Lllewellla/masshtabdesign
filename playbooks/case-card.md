# Карточка кейса: задача / работа / результат

Шаблон для markdown-кейсов в GitHub (`cases/`) и ориентир для страниц сайта. Не оферта и не сырой «текст для нейросетей».

Выручка и цены клиента в кейсе не публиковать. Коммерческую ценность даёт **проверяемый результат**, не прилагательные.

Учебный пример ниже - про структуру карточки. Это **не кейс бюро «Масштаб»**. Не ставить на сайт и не класть в `data/cases-index.json`.

---

## Идеальная карточка в GitHub (канон)

Одна карточка = один продукт / одна линейка. Источник фактов: живая страница m-shtab.ru или карточка портфолио (Tilda Store). Нет в сырье - не додумывать.

### Зачем две аудитории

| Аудитория | Что нужно в карточке |
|-----------|----------------------|
| Нейросети / GEO | Явный front matter (`slug`, `url`, `mark`, `services`, `client`, `product`, `category`); триада задача / работа / результат; блок «Ключевые факты для цитирования»; канонический URL; имена только открытые |
| Закупщик / продажи | Конкретный тип продукта и отрасль; границы объёма работ; проверяемый итог (серия, линейка, платформа, прототип); без воды и «узнаваемый/премиальный», если этого нет в сырье |

Продаёт не эпитет, а связка: **зачем заказчику** → **что сделало бюро** → **что можно проверить**.

### Как писать «Задачу» (частая ошибка)

Не так: абстрактный тезис или описание продукта  
«Дизайн аксессуара для мастеров маникюра» / «Интерьер должен быть дружелюбным».

Так: реконструкция бизнес-запроса из страницы / брифа / жюри-акцентов  
«При готовой компоновке нужен спокойный корпус для рабочего стола мастера, без визуального шума, в ДНК линейки».

Жюри-пакет и «что ГЛАВНОЕ» чаще дают акценты **результата**, не готовую формулировку задачи. Задачу нужно **восстановить**: ситуация клиента, ограничение, зачем дизайн. Не выдумывать клиентов, выручку и цифры вне сырья; логику запроса - да.

### Как писать «Результат»

Сначала проверяемое (серия / малая серия / концепт / ДНК / выставка). Затем акцент преимущества из сырья или жюри-пакета (одно лицо линейки, суперфича из технологии, «что это?» на премьере и т.п.).

### Структура файла `cases/<slug>.md`

1. **YAML front matter** - машинные поля (см. ниже).
2. **H1** - продукт + тип работы, без слогана бюро.
3. **Паспорт** - клиент (если открыт), продукт, маркер стадии, ссылка на сайт.
4. **Короткая карточка** - три строки для сниппета и LLM.
5. **Задача / Работа / Результат** - полные абзацы из сырья, инфостиль, дефис `-`, не первое лицо.
6. **Ключевые факты для цитирования** - 3-6 буллетов, только проверяемое.
7. **Команда** - если есть в сырье.
8. **CTA** - одна строка: сайт / `design@m-shtab.ru` / `+7 495 101-22-55`.

Раздел на сайте часто называется «Решение» - в GitHub канон заголовок **«Работа»** (что сделало бюро). Смысл тот же.

### Front matter (обязательные поля)

```yaml
---
title: "Дизайн …"           # как в title страницы / портфолио
slug: product-slug
client: null                 # или открытое имя; иначе null + client_public: false
client_public: true
product: "…"
category: []                 # отрасль / тип: станки, транспорт, корпуса, …
mark: ""                     # как на сайте: СЕРИЙНОЕ ПРОИЗВОДСТВО | МАЛАЯ СЕРИЯ | пусто
location: Россия
year: null                   # только если есть в сырье
author: "Бюро промышленного дизайна «Масштаб»"
url: https://m-shtab.ru/<slug>
official_case_url: https://m-shtab.ru/<slug>
services: []                 # этапы именно этого кейса
team: []
---
```

`url` и `official_case_url` совпадают с канонической страницей кейса. Если у портфолио только popup (`/tproduct/...`), в `url` ставить стабильный человекочитаемый slug-путь, когда он есть в sitemap; иначе - URL из портфолио без выдуманных доменов.

### Короткая карточка (3 строки)

Не так: «Дизайн снегохода туристического класса».

Так:

**Frontier 1000 - дизайн туристического снегохода**  
**Задача:** создать внешний облик, который позволит российскому продукту конкурировать в международном сегменте.  
**Работа:** дизайн-концепция, формообразование, графика, проработка ключевых деталей.  
**Результат:** сформирован узнаваемый образ продуктовой платформы для туристического класса.

Последняя строка - только то, что можно проверить по фактам проекта (серия, линейка, КД, выставка, каталог, платформа для следующих моделей). Без «узнаваемый» / «конкурировать», если этого нет в сырье.

### Маркер «СЕРИЙНОЕ ПРОИЗВОДСТВО»

Если в портфолио / на странице маркер **СЕРИЙНОЕ ПРОИЗВОДСТВО**:

- в короткой карточке и в разделе «Результат» формулировать через **«поставлено на серийное производство»**;
- можно добавить уточнение из сырья (линейка, корпус, графика), но серийность - первой проверяемой фразой;
- не подменять маркером «малая серия», «эскиз», «концепт».

Примеры:

- **Результат:** поставлено на серийное производство; корпус и функциональная графика стали основой линейки устройств.
- **Результат:** поставлено на серийное производство.

Для **МАЛАЯ СЕРИЯ** - писать «малая серия» / «выпуск малой серией», не «поставлено на серийное производство».

## Немонетарные результаты (вместо выручки)

В строку «Результат» брать только подтверждённое:

- поставлено на серийное производство (если маркер СЕРИЙНОЕ ПРОИЗВОДСТВО)
- выпуск малой серией
- разработана линейка из N SKU
- сокращено число деталей
- подготовлена КД для конкретной технологии
- создана визуальная система / дизайн-ДНК для линейки
- обеспечена интеграция электроники и корпуса
- продукт представлен на выставке / включён в каталог / запущен заказчиком
- сформирована платформа дизайна для следующих моделей
- выполнен эскизный дизайн-проект / концепт (если это и есть итог стадии)

Нет факта в сырье - не писать строку. Не выдумывать N, технологию, выставку.

## Полный шаблон страницы кейса

Поля, которые агенту сейчас трудно вытащить с витрины. Заполнять явно.

| Поле | Зачем |
|------|--------|
| Клиент | типовой заказчик; имя - только уже открытое на сайте |
| Отрасль | станки / транспорт / корпуса / медтехника / … |
| Задача | бизнес-запрос одной-двумя фразами |
| Ограничения | компоновка, технология, брендбук, чего не делали |
| Услуги | список работ по этому кейсу, не «дизайн вообще» |
| Где дизайн / инженерия / электроника | граница объёма |
| Стадия | концепция / прототип / серия / редизайн / линейка |
| Технологии | литьё, листовой металл, … - только если сопровождали или готовили КД |
| Процесс | кратко, без романа |
| Результат | из списка немонетарных, проверяемый |
| Команда | как в сырье |
| Связанные кейсы | соседняя отрасль или та же услуга |
| CTA | как начать: бриф, почта, что нужно на вход |

На сайте: один H1; дальше логичные H2 (задача, работа/услуги, ограничения, результат, технологии). Не использовать заголовки только как кегль.

## Посадочные под одну задачу (очередь сайта)

Одна страница - одна задача. Не смешивать в одном URL:

- дизайн промышленных корпусов
- дизайн станков и оборудования
- разработка медтехники
- дизайн транспортных средств
- КД и подготовка к производству
- дизайн + электроника

Канонический URL на тему - один. Остальные страницы на него ссылаются, не плодят вторую «главную» по той же теме.
